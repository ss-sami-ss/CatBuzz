# برنامهٔ آزمون و پذیرش

## رویکرد

برای reducer و قواعد حساس آزمون واحد، برای transaction/policy/API آزمون integration و برای مسیرهای اصلی آزمون end-to-end نوشته شود. ابزارهای پیشنهادی Vitest و Playwright هستند و در T02 با stack تثبیت می‌شوند. snapshot به‌تنهایی معیار پذیرش نیست. هر تسک خروجی قابل مشاهده و شواهد آزمون دارد.

## کیفیت و CI

format/lint، typecheck، تست‌های مرتبط و production build در CI اجرا شوند. dependency و secret scan با ابزار منتخب انجام شود. مرورگر موبایل واقعی یا شبیه‌سازی معتبر برای بار نقشه و push بررسی شود. خطای بحرانی امنیتی، مالی و از دست رفتن داده مانع اعلام آمادگی انتشار است.

## پذیرش انسانی

کارفرما مسیرهای ثبت گربه، درخواست کمک، پذیرش و ثبت نتیجه را با دادهٔ staging انجام دهد. دامپزشک جریان پرونده و ویزیت را بررسی کند. مشاور مسیر رضایت و لغو را ببیند. مسئول مالی پرداخت sandbox، refund و مغایرت را تأیید کند. نتیجه، تاریخ، نسخه و موارد باز ثبت شود؛ تأیید فرضی نوشته نشود.

## قالب شواهد

شناسه تسک / commit / محیط / فرمان یا سناریو / نتیجه / لینک تصویر یا لاگ پالایش‌شده / محدودیت / نام بازبین. وضعیت فعلی همهٔ Qها «اجرا نشده» است؛ این بسته تنها برنامهٔ تست است.


### پذیرش T14 روی staging

سناریوی `tests/e2e/cats.spec.ts` با `CATBUZZ_TEST_BASE_URL` به محیط آزمون مستقر متصل می‌شود و سرور محلی راه نمی‌اندازد. `CATBUZZ_TEST_MAILPIT` باید به inbox آزمایشی همان محیط اشاره کند تا سناریوی ثبت واقعی اجرا شود. از حساب و دادهٔ آزمایشی استفاده می‌شود.

```powershell
$env:CATBUZZ_TEST_BASE_URL = '<staging-origin>'
$env:CATBUZZ_TEST_MAILPIT = '<staging-test-inbox>'
npm run test:e2e -- cats.spec.ts
```
